01 Broad retrieval, reranking, and token packing

Retrieve for recall first. Then rank and pack evidence for answer quality.

Direction agreed

What: Retrieve a broad hybrid candidate pool, rerank it, then pack the strongest complete evidence into the source budget.

Why: A fact lookup and a multi-paper comparison need different amounts of evidence.

Context: Keep document, section, element, caption, and page labels through indexing and citation output.

Status: Implemented. The 24-item run selected depth 20, MiniLM, penalty 0.15, and 12,000 source tokens.

Do not use a fixed final chunk count as a product rule.

A result count such as ten is an evaluation setting, not proof that ten chunks suit every question.

02 Implementation contract

The runtime uses this deterministic path before any adaptive retrieval loop.

message
  -> QueryPlan with strict JSON output
  -> one to three SearchIntents
  -> hybrid search for each intent
  -> RRF fusion, deduplication, and cross-encoder reranking
  -> diversity-aware token packing
  -> grounded answer with exact citations
One SearchIntent

A SearchIntent represents one distinct evidence need, not one user message.

A direct question and a context-resolved follow-up create one intent.

A comparison or request with separate aspects creates two or three intents.

{
  "action": "retrieve | clarify",
  "search_intents": [
    {
      "dense_query": "What doses and adverse events were reported in the Hickson senolytic trial?",
      "sparse_query": "Hickson senolytic dose adverse events",
      "filters": {}
    }
  ]
}

Rules for the QueryPlan

  1. Default to one intentCreate more only when the message asks for separate evidence, such as a comparison, several entities, or distinct requested aspects.
  2. Use two query formsThe dense query carries the complete resolved meaning. The sparse query keeps exact entities for BM25.
  3. Preserve literal scientific termsCopy paper IDs, authors, drug names, doses, years, numbers, and quoted phrases from the message or conversation history.
  4. Resolve, do not inventUse history to resolve “it” or “the other trial.” Do not add facts, inferred entities, or generated synonyms.
  5. Clarify absent intentIf the user only supplies material, return clarify instead of searching without a stated task.

Retrieval for each SearchIntent

  1. Embed the dense querySearch the vector index with the semantic query.
  2. Search the sparse querySearch BM25 with the exact lexical terms.
  3. Fuse broad candidatesUse RRF to combine the dense and BM25 candidate lists.
  4. Merge intent resultsDeduplicate the union from every SearchIntent before reranking.
  5. Pack complete evidenceSelect diverse retrieved chunks until the source-token budget is full.
Measured requirement

The calibration compared the PR 31 baseline, raw-only, dual-query, and aspect-decomposed variants.

The final depth-20 pipeline passes all three blocking document-level gates.

03 Turn a message into retrieval queries

One user message can need zero, one, or several retrieval queries.

Query plan

A short model call reads the current message and saved conversation history.

It returns query strings for semantic search, exact lexical anchors for BM25, and optional paper or author filters.

{
  "action": "retrieve | clarify",
  "search_intents": [{
    "dense_query": "full semantic question or aspect",
    "sparse_query": "verbatim paper, author, drug, dose, year, phrase",
    "filters": {"document_id": null, "author": null}
  }]
}

Each dense query must resolve references such as “it” or “the other trial.”

The plan can return multiple queries for a comparison or independent requests in one message.

It must not add scientific facts, synonyms, or inferred entities.

If a user only pastes material, it returns clarify instead of inventing a research task.

04 One deterministic retrieval path

  1. Build searchable textPrepend paper, section, element, caption, and page labels to each original chunk.
  2. Index both signalsEmbed the searchable text and store the same text in the BM25 index.
  3. Plan retrievalCreate zero, one, or several semantic queries and a lexical-anchor list.
  4. Search broadlyRun dense and BM25 search with each intent's distinct query form.
  5. Fuse and rerankDeduplicate candidates, fuse ranks, and rerank the combined pool.
  6. Pack evidenceAdd diverse, complete evidence units until the source-token budget is full.
Deterministic context

The indexed header uses labels such as Paper, Section, Element, and Page.

The researcher receives the original chunk text. No LLM generates or rewrites this context in v1.

Why the planned variants regress

A4 asks for both metformin and rapamycin. The raw and dual top 10 repeat paper 012, so paper 013 never enters the document set. Aspect planning adds paper 019 but still omits 013.

B2 asks for D+Q doses in idiopathic pulmonary fibrosis. Raw and dual rank the lookalike diabetic-kidney paper 015 above the gold IPF paper 016. Aspect planning reverses that order and passes B2.

The 10-candidate controls show a recall and ranking failure, not a gold-document failure. Every variant still reaches 12/12 gold items and C1.

07 2026 research supports the direction

The strongest sources support separate lexical and semantic queries, plus multiple queries for multi-aspect messages.

SourceFindingUse here
DVCQR, ACL 2026Separate sparse lexical and dense semantic rewrites improve conversational retrieval.Plan lexical anchors separately from embedding queries.
MQ4CS, EACL 2026Multiple aspect queries beat one rewrite for complex conversational requests.Allow several queries when one message needs independent evidence.
QueStER, EACL 2026Generated keyword specifications improve lexical retrieval.Use verbatim scientific anchors in the BM25 query.
SemEval Task 8, 2026A training-free pipeline combines rewriting, hybrid search, and cross-encoder reranking.Keep the first system deterministic and evaluate each added stage.
Adaptive RAG robustness, 2026Equivalent wording can change adaptive retrieval behavior.Evaluate raw and planned queries together.
Evidence boundary

These sources support the architecture direction. They do not prove one candidate depth, source budget, or reranker for this corpus.

Use the same index, embedding model, and 24-item query set for every retrieval comparison.
