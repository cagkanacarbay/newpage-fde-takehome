Set The corpus Set

27 open-access research papers on the biology of aging — mechanisms of aging, biomarkers of biological age, and interventions that aim to extend healthspan. Chosen because answering questions across a body of research literature is a use case a client plausibly has, and because it is genuinely hard: long documents, dense technical language, heavy tables, and papers that contradict each other.

27papers
425pages
7papers with displayed equations
6contradiction pairs

Everything is from the PubMed Central Open Access subset, fetched from Europe PMC. No paywall was bypassed.

GitHub coverage

Issue #4 records the 27-paper Europe PMC corpus and its provenance.

Why this set is hard on purpose

  • Dense topical overlap. Six papers cover epigenetic clocks, five cover senescence, four evaluate a small-molecule drug. Keyword-matching “aging” retrieves everything, so it retrieves nothing useful.
  • Six contradiction pairs. Do senolytics reverse aging? Papers 015/016 say yes, 017 says no. Does chemical reprogramming rejuvenate? 019 says yes, 020 finds it toxic. Is metformin a geroprotector? 012 is critical, 013 finds rapamycin works and metformin does not. A question can be answered two opposite ways depending on what got retrieved — which makes faithfulness measurable rather than a matter of opinion.
  • Named-entity traps. rapamycin vs trametinib · dasatinib vs quercetin vs fisetin · PhenoAge vs GrimAge vs DunedinPoAm. Semantic similarity alone blurs these; they are exactly where lexical matching earns its place.
  • Answers that live only in tables. “Which biomarker predicted mortality best” is answerable from one table in paper 009 and nowhere else. That single question tests the whole parsing layer.
  • Wildly uneven length. A 1-page PNAS letter next to a 32-page research article. Any chunking strategy has to survive both.

How it is stored

The PDFs are not committed to the repository. The script scripts/fetch_corpus.py rebuilds the corpus from source, pinned by PubMed Central ID, and verifies every file by extracting text from every page. Re-downloads are byte-identical to the originals. Keeps the repo small and makes the corpus provenance explicit rather than a folder of mystery PDFs.

What settles it

Two questions, not one. Is the retrieval code itself part of what we are showing, or is it plumbing better bought so the hours go into the frontend and the evaluation? And if we buy it, core with every argument named, or the bundle with defaults? The second answers itself. The first is the real call — see 02a.

The answer

It takes away none of the nine. Every one is an explicit argument we pass. What it removes is the labour of implementing the alternatives — which makes comparing them cheaper, not harder. Testing four chunking strategies against a golden set is a day of work by hand and an afternoon with the library.

So is there any reason not to use it?

Yes — five, and one of them is serious.

1 — The code stops being the work sample the serious one

The brief grades "clean, readable, well-structured code that others can understand." A repository that is mostly configuration of somebody else's abstractions shows less engineering than one where the ingest and retrieval loop is visibly ours. A reviewer reading SentenceSplitter(chunk_size=512) cannot tell whether that number was chosen or inherited.

This is the only argument here that a framework cannot answer, because it is not about capability.

2 — An abstraction between us and the bug

When retrieval returns the wrong chunk, debugging goes through the library's layers rather than through our own two hundred lines. At this corpus size a hand-rolled pipeline is small enough to hold in your head; the framework never is.

3 — The defaults are right there

VectorStoreIndex.from_documents(docs).as_query_engine() is two lines and a working RAG system. The risk was never that the framework removes our choices — it is that it makes not choosing frictionless, and then the README has nothing to say. Avoidable, but only by discipline.

4 — Dependency weight and version churn

Even llama-index-core carries a real dependency tree, and the project moves fast enough that pinning matters. A hand-rolled pipeline over Qdrant and an embedding model is roughly five dependencies.

5 — It does not help where this corpus is actually hard

Guardrails: nothing shipped. Getting both sides of a contradiction into one context: mostly custom either way. Making a citation point at a PDF page: ours. The layers where these twenty papers make life difficult are largely the layers the framework does not cover — so the saving is real but it lands on the easy parts.

The distinction that carries the decision

llama-index          starter bundle, pre-selected integrations, defaults on
llama-index-core     base package, every integration added deliberately

Taking core and naming every argument gives the library's breadth with none of the silent defaults, and the resulting code reads as explicit composition rather than framework magic.

Where this lands

There is a middle path that answers objection 1 without giving up the rest: take the commodity pieces from the library — readers, node parsers, BM25, fusion, the evaluation metrics — and write the orchestration ourselves, so the ingest and answer paths are our code calling named components. That is defensible in the README as a deliberate boundary rather than a default, and it keeps the hours for the frontend. Still Cha's call.

Licence is not a footnote here

Three of the six are copyleft: MinerU and PyMuPDF4LLM are AGPL-3.0, Marker is GPL-3.0. Workable for a public repository, but it propagates — and it is a real strike against the two strongest scientific-PDF parsers on the list. Docling (MIT) and unstructured (Apache-2.0) are the only permissive open options.

Docling — the permissive all-rounder

For Markdown with real heading hierarchy, which is what choice 04's structural option depends on. TableFormer is the strongest open table extractor on nested tables. Pure-Python install, runs on CPU, MIT, IBM-maintained.

Against Slower per page than the lightweight options. Formula handling is weaker than MinerU's, which matters for a corpus with LaTeX-set equations.

MinerU — built for exactly these documents

For Purpose-built for academic PDFs. Best multi-column layout detection here, and the only one with dedicated formula recognition. On capability alone it is the closest fit.

Against Heaviest install by far — model weights, optional GPU, a much fatter container, and more to go wrong in someone else's setup. AGPL-3.0.

Marker — the fast middle

For Meaningfully faster than Docling and MinerU because its models are lighter, with good structure fidelity and solid formula handling.

Against Weaker than Docling on nested tables, which is where this corpus hides several answers. GPL-3.0.

PyMuPDF4LLM — instant, and probably too weak

For Trivial install, no ML, near-instant. Would turn ingestion of the whole 425-page corpus into seconds and remove a class of setup problem.

Against No layout intelligence. Two-column reading order is unreliable and tables flatten into noise — and it fails silently, producing plausible text with two columns interleaved. On this corpus that is the worst failure mode available. AGPL-3.0.

unstructured — an ETL layer more than a parser

For Broadest format coverage, Apache-2.0, built as an ingestion pipeline — useful if choice 01 lands on user uploads of mixed formats.

Against The high-accuracy path is the hosted API. The open version is noticeably weaker on precisely the two-column, table-heavy layouts here.

LlamaParse — best output, at a price

For Excellent table and layout handling with nothing to install. Removes the parsing risk entirely in exchange for an API call.

Against API key, per-page cost, and documents leave the machine — a hard dependency in "quick setup instructions", and an awkward property for a system whose premise is a private document collection.

The three questions that actually decide it

Everything else on the matrix is speed and install weight. These three are pass/fail:

Does it emit heading hierarchy? If not, structural chunking is off the table and choice 04 collapses to recursive or semantic.
Does it carry page numbers? If not, a citation cannot point at a page. For research papers a citation the reader cannot check is decoration.
Do tables survive as structure? If not, "which biomarker predicted mortality best" is unanswerable — that answer lives in one table in paper 009 and nowhere else.
What settles it

Capability points at MinerU; licence points away from it. Docling is the only option that clears all three gates and carries a permissive licence, which makes it the one to beat rather than the obvious winner. Whether the formula and multi-column gap against MinerU is real on these twenty papers or only real on a benchmark is cheap to find out — the corpus is already on disk.

04 Chunking Open

GitHub coverage

Issue #10 is closed. The recorded answer remains provisional: use Docling HybridChunker with flat retrieval until the corpus gates pass.

Chunking research.

Determines what a retrieval hit physically is — and therefore whether a hit contains enough context to answer with, or so much that the signal is diluted.

OptionWhat you getWhat it costs
Fixed-size windows Dead simple, uniform, predictable token budgets. Cuts through sentences, tables and arguments. The baseline everything else is measured against.
Recursive character Splits on paragraph, then sentence, then character. Cheap, deterministic, respects obvious boundaries. Blind to document structure. A methods section and a discussion section chunk identically.
Structural / section Uses the document's own headings as hard boundaries; a chunk never crosses a section. Free, deterministic, and research papers have unusually good structure (Abstract, Methods, Results, Discussion). Entirely dependent on choice 03 producing real headings. Section lengths vary enormously, so it needs a size cap and a split rule anyway.
Semantic Places boundaries where embedding similarity drops. Works on any text, including unstructured output. Costs an embedding pass over every sentence at ingest. Boundaries are hard to explain and harder to debug.
Neural boundary model A trained model predicts paragraph boundaries directly (Chonky and similar). Better than heuristics on prose with no markup. Another model to ship and run. Trained on general prose, not scientific papers.
Late chunking Embed the long document first, then pool per chunk, so every chunk vector carries whole-document context. Strong on documents full of pronouns and back-references. Needs a long-context embedding model, which constrains choice 06. Less widely proven.
Parent–child Match on small precise chunks, hand the model the larger parent. Decouples match size from context size. Two indexes, more machinery. Choice 05 can achieve most of the same effect more cheaply.
What settles it

Choice 03, almost entirely. If the parser gives clean headings, structural chunking is available, free, and easy to defend. If it gives a wall of text, the real contest is between recursive and semantic. Deciding chunking before parsing would be deciding it blind.

Number from earlier work

On a 28-page Wikipedia corpus, structural chunking scored MRR 0.82 against 0.73 for LLM-written contextual chunking, which cost $1.70 to produce. Parent–child was far behind both. That was markup-native input with perfect headings and a retrieval-only evaluation — worth knowing, not worth assuming. Research PDFs are a different input.

05 Chunk metadata & the citation unit Open

GitHub coverage

Determines what a source looks like in the UI, whether a reader can verify a claim, and what we can filter retrieval by.

Two separable decisions. What we store on every chunk: document ID, title, first author, year, DOI, page number, section path, character offsets. Each one is either a filter, a citation field, or dead weight. What the user is shown as the source:

OptionWhat you getWhat it costs
Show the chunk Zero extra work — the retrieved text is the citation. Chunks read as fragments. A reader lands mid-argument with no way to check the surrounding claim.
Match small, show the section around it The chunk only has to be good enough to match; the reader gets the coherent passage around it, with the matched span highlighted. Removes most of the pressure from getting chunk size exactly right. Needs character offsets tracked through the whole pipeline, from parser output to stored chunk.
Link to the PDF page The strongest possible answer to “how do I know that is true” — the reader sees the actual page of the actual paper, with the DOI beside it. Needs reliable page numbers from choice 03, PDF serving, and a viewer in the frontend. The most frontend work of the three.
What settles it

These are research papers, so a citation the reader cannot check is decoration. Page number plus section path is the floor. The real question is whether showing the actual PDF page is worth the frontend time, given that it is also the single most convincing thing in a demo.

OptionWhat you getWhat it costs
Qdrant Native named dense + sparse vectors with built-in fusion, so hybrid search is a single round trip. Strong payload filtering and indexes. Runs embedded from a local path or as a container. Another service in the deployment story if run as a container.
pgvector One database for vectors and application data. Universally understood, trivially deployable on every hyperscaler — which matters for the productionization section of the README. This is a decision about the architecture story and the code we have to write, not about performance.

08 Retrieval strategy Open

GitHub coverage

Issue #15 is open. It covers the retrieval approach and hybrid-fusion verdict. Issue #26 carries retrieval in the architecture and build slices.

Determines what text actually reaches the model — the single thing that most decides whether an answer is right.

This corpus has two properties that push in different directions, and the strategy has to handle both.

  • Entity traps push toward lexical matching. “rapamycin” and “trametinib” are near-neighbours in embedding space and completely different drugs. Dense retrieval alone blurs exactly the distinctions these questions turn on.
  • Contradiction pairs push toward diversity. Ask “do senolytics reverse aging” and plain top-k by similarity can return five chunks that all agree, because they are the most similar chunks — and the model will then answer with total confidence and be half wrong. Getting both sides in front of the model is a retrieval problem, not a prompting problem.
OptionWhat you getWhat it costs
Dense top-k The simplest thing that works. One query, no fusion, easy to reason about. Misses exact terms, drug names and acronyms. No defence against retrieving five chunks that all say the same thing.
Hybrid dense + sparse BM25 catches the exact entity, dense catches the paraphrase, reciprocal rank fusion merges them. Directly addresses the entity traps. Sparse index to build and keep in sync. Fusion weighting is another knob with no obvious right value.
+ Reranker A cross-encoder rescores the top 50 down to the top 5, reading query and passage together. Usually the largest single quality gain available. Another model, and latency on every query. An API reranker adds a second vendor; a local one adds weight.
+ Diversity / per-document cap Limits how many chunks any one paper can contribute, so opposing findings survive into the context. The direct answer to the contradiction problem. Can dilute results for questions that genuinely live in a single paper. Needs tuning against real questions.
+ Query rewriting The model turns a vague or conversational question into a good retrieval query. Overlaps heavily with choice 09. An LLM call before every search: latency and cost on the critical path, and a new failure mode when the rewrite is wrong.
Graph traversal Retrieve by walking entity relationships rather than similarity. Genuinely better at “what does the literature collectively say about X”. Expensive graph construction at ingest and a large jump in system complexity. Effectively pulls choice 02 toward a framework.
What settles it

Whether we treat “surface the disagreement” as a core product behaviour or an edge case. If it is core — and this corpus was picked because it is — then plain top-k is not enough, and the choice is which of the additions above earns its latency. Each one is independently switchable, so this can be built as a baseline plus measured increments rather than one big bet.

09 Multi-turn handling Open

GitHub coverage

Issue #22 is open. It covers the context-management strategy for multi-turn behavior. Issue #26 carries the wider architecture boundary.

Determines whether the thing is actually conversational. The brief says “conversational AI assistant”, and a demo gets judged on a conversation, not a single question.

The failing case is short: ask “what did Hickson find about senolytics”, then ask “what about the other trial”. Retrieving on that second message alone returns nothing useful, because on its own it means nothing.

OptionWhat you getWhat it costs
No history Every message retrieves independently. Simplest, fastest, fully stateless. Follow-up questions break. This is the first thing a reviewer will accidentally test.
Concatenate recent turns Prepend the last few messages to the retrieval query. Two lines of code, no extra model call, fixes the common case. Drags stale topics into the query. Three turns later the search is polluted by an abandoned subject.
LLM query rewriting A small model rewrites the follow-up into a standalone question before retrieval. The standard solution, and it works well. An extra model call before every search — latency the user feels, plus a new way to fail silently when the rewrite drops a constraint.
Carry context forward Keep previously retrieved chunks in the window alongside new ones. No extra call, and follow-ups about already-discussed material are instant. Context grows every turn. Needs an eviction rule, and stale chunks compete with fresh ones.
Agentic loop The model decides whether to retrieve, how, and whether to search again after seeing results. Handles multi-part questions properly. Several model calls per answer, unpredictable latency, and much harder to evaluate deterministically.
What settles it

How much per-turn latency the chat can absorb before it stops feeling responsive, and whether we want a deterministic retrieval path we can evaluate — an agentic loop is much harder to score against a fixed question set, which pulls directly against choice 13.

10 Generation model Open

GitHub coverage

Issue #18 is open. It covers the OpenAI versus Gemini model lineup. Issue #23 covers generation and streaming behavior, while Issue #25 covers production model serving.

No final generation-model decision is recorded.

Determines answer quality, per-answer cost, streaming latency, and how reliably instructions about citing and refusing are actually obeyed. Named explicitly in the brief as something to justify.

OptionWhat you getWhat it costs
Claude Sonnet 5 Strong instruction-following on citation format and refusal rules, good long-context handling with many sources, fast streaming. The balanced default. API key and per-token cost.
Claude Haiku 4.5 Much cheaper and faster. Well suited to the smaller jobs around the edges: query rewriting, groundedness checking, routing. Weaker at synthesising several conflicting sources into a careful answer.
Claude Opus 5 Best at exactly the hard case here: several papers disagreeing, and the answer needs to represent that accurately. Highest cost and slowest. Hard to justify for every turn of a demo.

Whether one model serves every job or we split them — a cheap fast model for query rewriting and groundedness checks, a stronger one for the answer. Splitting is better engineering and is easy to explain, at the cost of a second model in the config. Worth deciding alongside choices 09 and 12, which are where the small jobs live.

11 Context assembly & prompt Open

GitHub coverage

Issue #22 is open. It covers context management, and Issue #23 covers generation, prompts, and citation-to-page behavior. Issue #24 covers streaming output and exact citation presentation.

No final prompt or context decision is recorded.

Determines whether answers stay grounded, whether citations point at the right source, and what the system does when the retrieved passages disagree with each other.

Several smaller decisions travel together here:

  • How many chunks, and how they are ordered. By relevance, or reassembled into document order so an argument reads in sequence.
  • Whether metadata rides along. Title, authors and year in the context let the model write “Hickson 2019 found…” instead of “one study found…”. Cheap, and it changes how the answer reads entirely.
  • Citation mechanism. Inline markers the model emits, versus structured source objects the UI renders separately. The first is simpler; the second cannot be hallucinated.
  • Behaviour when nothing relevant comes back. The most important prompt decision, and the one most often skipped.
  • Permission to report disagreement. Unless the prompt explicitly allows “these papers conflict, here is each position”, the model will pick one and sound certain. On this corpus that is a wrong answer with full confidence, and it will happen in the demo.
What settles it

Whether structured citations are worth the extra plumbing. If the model emits “[1]” as text, it can invent a “[4]” that does not exist. If the UI renders sources from the retrieval result and the model references them by ID, a fabricated citation is structurally impossible. That is a guardrail bought with schema rather than with a prompt, and it is the kind of decision worth writing up.

12 Guardrails Set

GitHub coverage

Issue #21: Guardrails policy records the agreed policy. The decision page defines its evidence, citation, conflict, medical, and prompt-injection boundaries.

Issue #26 also carries guardrails in the architecture chain.

Determines what happens when retrieved evidence cannot answer a question, when a question is out of scope, and when document text tries to influence the model. Named explicitly in the brief.

OptionWhat you getWhat it costs
Prompt-level only “Answer only from the provided sources; if they do not contain the answer, say so.” Free, and it does most of the work. Nothing enforces it. Cannot be measured, and fails exactly when the retrieval was weak.
Retrieval score threshold If the best match is below a score, refuse before generating. Deterministic, costs nothing, and catches out-of-scope questions early. The threshold is arbitrary until measured, and similarity scores are not calibrated across queries.
Post-hoc groundedness check A second model call verifies each claim is supported by a retrieved chunk. Catches real fabrication, and the check itself is demonstrable in the UI. Doubles latency and cost per answer. Needs a decision about what to do on failure: warn, regenerate, or refuse.
Citation verification Deterministically confirm every cited source ID was actually retrieved. Cheap, exact, no model involved. Only catches invented citations, not claims that misrepresent a real source.
Input classification Screen the question before spending retrieval and generation on it. Another model call, and it fires on every message including the harmless ones.
What settles it

The policy is set: filter retrieval, verify claims, and validate citations. The remaining implementation choices are a measured relevance threshold and the verifier model. Measure latency and verifier accuracy against answerable, irrelevant, and conflicting corpus questions.

The curated corpus can still contain instruction-like text. Treat every retrieved passage as data, never instructions. User uploads increase that risk but do not change the policy.

13 Evaluation Open

GitHub coverage

Issue #19 is closed for the evaluation options, and Issue #20 is open for the final v1 quality gates. Research.

Issue #9 also tests equations as a parser-quality gate.

Determines whether every choice above is something we measured or something we asserted. “Quality Controls” is named in the brief, and this is where the README stops being opinion.

This corpus was chosen partly because it makes evaluation cheap: the six contradiction pairs are questions with a known right shape of answer, where a bad retrieval produces a detectably wrong result rather than a slightly worse one.

OptionWhat you getWhat it costs
Retrieval metrics on a labelled set Hand-label questions with the sections that should be retrieved, then score hit rate, MRR, recall@k and precision@k. Deterministic, free, instant, and it turns every choice above into a comparison. Labelling questions by hand. Measures retrieval only — an answer can still be wrong from perfect context.
Generation faithfulness Score whether the answer is supported by the retrieved context. Covers the half the retrieval metrics cannot see. Needs a judge model: tokens, run-to-run variance, and a judge whose own accuracy is unverified.
ragas An off-the-shelf harness with the standard metric set already implemented. Its precision and recall are LLM-judged rather than label-based — token cost and variance between runs, for metrics we could compute exactly against our own labels.
promptfoo / DeepEval Config-driven, good CI story, assertion-style tests that fit the existing test discipline. Another tool in the stack, and the interesting metrics still need custom code.
None, argued honestly All the build time goes into the product. The brief does explicitly accept documenting what you would add next. Every claim in the README becomes an assertion, in a submission judged on engineering rigour.
What settles it

Whether an evaluation exists at all is barely a question — some measurement is worth far more than none. The real decision is scope: retrieval-only is cheap, deterministic and immediately useful for comparing choices 03, 04, 06 and 08. Adding generation-side scoring costs a judge model and gets us the faithfulness numbers, which is the half that matters on a corpus full of contradictions.

14 Observability Open

Decision from closed issue

Issue #17 is closed. Decision: use Arize Phoenix for the demo.

TL;DR: Keep RAG traces local, visible, and portable through OpenTelemetry. Decision page · Issue #25 covers production observability.

Determines whether a bad answer can be diagnosed — which chunks were retrieved, with what scores, what the prompt actually contained, and where the latency went. Named in the brief.

OptionWhat you getWhat it costs
Phoenixself-hosted Purpose-built for RAG traces, OpenTelemetry-based, runs from a short compose file. No account, no free-tier ceiling, works for a reviewer offline. Another container. Instrumentation has real pitfalls — synchronous span export can dominate ingest time if configured naively.
Langfuse Strong UI, prompt management and evaluation built in, self-hostable. Broad adoption. Heavier self-hosted footprint than Phoenix.
LangSmith Best experience if already in the LangChain ecosystem. Cloud only, needs an account, and the free tier has a monthly trace cap that a few evaluation runs can exhaust — at which point the whole workspace throttles.

Structured logs only Nothing to deploy. Retrieval scores and timings in the log are genuinely enough to debug at this scale. Nothing to show a reviewer. Observability becomes a claim rather than a screenshot.
What settles it

Whether it has to work for a reviewer with no account and no signup — which rules out everything cloud-only. Beyond that, whether tracing is instrumentation we use while building, or a surface we intend to show off. If the latter, it belongs in the same compose file as the app.

15 Frontend & packaging Open

GitHub coverage

Issue #5 is closed for the web stack. Issue #24 covers the chat surface, and Issue #25 covers production packaging. Issue #26 covers the build slice.

No final frontend or packaging decision is recorded beyond the existing web-stack choice.

Determines how the work is judged on sight, and how much setup friction stands between a reviewer and a working app. The brief asks for creativity in UI/UX and says outright that it expects a well designed application.

OptionWhat you getWhat it costs
Streamlit / Gradio A working chat interface in an afternoon, in the same language as the backend. Maximum time left for retrieval quality. Looks exactly like every other RAG demo, and the brief explicitly asks for design. Hard to build a real citation viewer in.
Next.js Full control of the design, proper streaming, and room for the source panel and PDF viewer that make the citations convincing. A second language and toolchain, a build step, and real frontend hours.
React + Vite Same design freedom, lighter than Next, no server-rendering machinery that this app does not need. Routing and data fetching are hand-rolled. Same frontend time cost.
Server-rendered + HTMX One language, one process, one deployable. Streaming answers work fine over server-sent events. Rich interaction — highlighting, a PDF pane, live source filtering — gets awkward fast.

Packaging is a separate call: a single container, a compose file covering app plus vector store plus tracing, or plain local commands with no container at all. The brief asks for “ideally a simple containerised solution”, and the productionization section has to explain how this reaches a hyperscaler.

What settles it

Where the differentiation is supposed to come from. Option 1 is the option everyone picks, so the engineering and the interface are the only places to stand out. Streamlit spends nothing on that and leaves more time for retrieval. A real frontend spends real hours and is the most visible thing in the submission. This is a budget decision more than a technical one, and it is worth making with eyes open rather than by default.
