01 The production boundary

Keep the proven retrieval and citation contracts. Replace every machine-local state boundary before adding replicas.

Current One image Exported Next.js UI, FastAPI, the index, and source PDFs.
Current Local state LanceDB in the image and SQLite on one mounted volume.
Production Shared services PostgreSQL, object storage, managed search, and a job queue.
Production Controlled access Customer identity, tenant filters, audit records, and trace policy.
The image cannot scale unchanged

Two copies would have separate SQLite files, separate writable indexes, and separate PDF filesystems.

A load balancer could send one conversation to different copies and produce conflicting state.

The production target keeps the API contract, hybrid retrieval, MiniLM reranking, token packing, and exact citation geometry.

It moves conversations, papers, parent sections, and search indexes behind services that all API replicas can reach.

Keep The verified application path FastAPI, server-sent events, OpenAI, query planning, hybrid retrieval, reranking, and citation-to-PDF.
Replace Machine-local ownership SQLite, embedded writable search, local PDF serving, manual ingestion, and unauthenticated access.

02 Stateless API runtime

A FastAPI replica should own no durable user or corpus state. Any healthy replica should serve the next request.

  1. Separate the static UIPut immutable web assets behind a CDN. Route only /api/* and protected PDF access to FastAPI.
  2. Externalize all stateUse PostgreSQL for conversations, object storage for papers and parent text, and a managed search service for chunks.
  3. Preserve streamingKeep server-sent events unbuffered. Set gateway idle timeouts above the maximum answer time and drain connections during deployment.
  4. Scale on useful signalsUse active streams, time to first token, CPU, memory, and queue delay. Request count alone hides long-lived streams.
  5. Protect dependenciesSet per-tenant concurrency limits, bounded retries with jitter, provider timeouts, and circuit breakers around OpenAI and search.
  6. Deploy safelyUse readiness checks, graceful shutdown, a small warm pool, canary traffic, and automatic rollback on error or citation failures.
No session affinity

Shared state removes the need for sticky sessions.

One streaming request stays on one replica until completion, but its completed turn commits to PostgreSQL.

03 State and search

SQLite and embedded LanceDB fit the local demo. They are not the shared write boundary for several API replicas.

Move conversations from SQLite to PostgreSQL

The current SQLite store uses WAL mode and one bind-mounted file.

That is simple and durable for one process, but it has one writer boundary and one volume failure domain.

04 Ingestion and auth

Ingestion becomes an asynchronous control plane. Customer identity controls every document and retrieval boundary.

Deferred ingestion pipeline

  1. Accept and quarantineAn authenticated user uploads a supported PDF. Store it in a private quarantine bucket and record its content hash.
  2. ValidateCheck size and type, scan for malware, reject encrypted or invalid files, and create an immutable document version.
  3. QueuePublish an idempotent ingestion job. Return a job ID and status instead of holding an HTTP request through Docling.
  4. Parse and indexAn isolated worker runs Docling, creates child chunks and parent sections, embeds in batches, and writes a staged index version.
  5. Check and promoteValidate citation geometry, chunk counts, and retrieval smoke cases. Promote the new index pointer only after all checks pass.
  6. Operate the lifecycleRecord retries, failures, model versions, costs, and audit events. Support deletion, reindexing, rollback, and dead-letter recovery.

Use the content hash, parser version, chunker version, embedding model, and index schema as the idempotency key.

Never edit an active index in place when a versioned build and atomic pointer swap can make rollback safe.

Customer auth boundary

Identity

Validate the customer's OIDC token at the edge or API. Convert it into stable tenant, user, and role claims.

Authorization

Apply tenant filters to PostgreSQL, search, ingestion jobs, object keys, and citations before data leaves each service.

Paper access

Serve PDFs through an authorized API or short-lived signed URL. Never expose a public corpus bucket.

Service identity

Give API and worker roles separate least-privilege credentials. Keep keys in the provider secret manager and rotate them.

External processing is a customer decision

Paper text, queries, conversation history, and generated answers reach OpenAI in the chosen design.

Confirm data residency, retention, contractual controls, and allowed content before production use.

Track tokens by pipeline stage. The unit price matters less than repeated history, output length, and retries.

StageCost behaviorControl
Document embeddingswrite-timeOne million new source tokens cost 1 x $0.13. Reindexing repeats the cost for changed inputs.Hash documents, embed only changed chunks, batch requests, and use the Batch API when a 24-hour completion window is acceptable.
Query embeddingsread-timeCost grows with the number and length of planned dense queries. Ten million query tokens cost 10 x $0.13.Cap planned intents, cache identical permitted queries, and reject retry storms.
Answer generationevery turnInput includes instructions, history, and up to 12,000 evidence tokens. Output tokens cost six times the Luna input rate.Measure cost per successful answer, cap output, preserve prompt-cache prefixes, and shorten history only through tested policy.
Planner and verifierextra model callsThe planner runs before retrieval. The planned verifier adds input and output for each claim or claim batch.Record both calls separately, batch supported claims, and route only after evaluation proves quality.
Long contextprice stepLuna prompts above 272,000 input tokens use higher input and output rates for the complete request.The current 100k history budget stays below that step before evidence, but measure the complete assembled prompt.

The cost formula for one answer is direct:

embedding query tokens x embedding rate
+ planner input and output tokens x Luna rates
+ answer input, cached input, and output tokens x Luna rates
+ verifier input and output tokens x Luna rates
  • Set budgets per tenant. Alert before limits and reject abusive work with a clear response.
  • Keep quality gates fixed. A cheaper model or smaller context ships only after the same retrieval and answer tests pass.
  • Measure retries as waste. Provider retries, disconnected streams, and duplicate ingestion must appear as separate cost counters.
  • Forecast from distributions. Use p50 and p95 history, evidence, output, and claims per turn. One average hides expensive research sessions.

06 Production observability

Keep Phoenix as the RAG trace surface. Give it production storage, access control, retention, and a failure-independent export path.

Trace one answer from edge to citation

01RequestTenant, route, request ID, and time to first byte.
02RetrievalPlan, embedding, search, rerank, packed tokens, documents, and pages.
03GenerationModel, token usage, cache usage, latency, refusal, and provider errors.
04VerificationClaim counts, support results, removed claims, and citation validation.
  1. Use portable instrumentationEmit OpenTelemetry and OpenInference spans from the API and workers. Export with asynchronous batching over OTLP gRPC.
  2. Protect research dataRedact prompt and response bodies by default. Use hashed user IDs and an explicit allowlist for source snippets.
  3. Run Phoenix separatelyPin its image version, enable authentication and TLS, and use managed PostgreSQL with backups and a tested restore.
  4. Set retentionUse separate development, staging, and production projects or instances. Set finite production retention from the customer policy.
  5. Alert outside PhoenixSend service metrics to the cloud monitor. Page on error rate, first-token latency, invalid citations, rate limits, and cost spikes.
  6. Keep telemetry non-blockingDrop or buffer telemetry under collector failure. Never delay or reject an otherwise valid answer because Phoenix is unavailable.

07 Parent-section expansion

The local demo stays flat. Production can retrieve precise child chunks, then expand selected evidence to its full section.

Deferred on purpose

Parent expansion needs new storage, index-version rules, token policy, and new evaluation.

Adding it to the 27-paper demo would add complexity before its value is measured.

Storage contract

RecordStored fieldsRole
Document versionTenant, source hash, object key, parser version, status, and index version.Immutable ownership and lifecycle boundary.
Parent sectionParent ID, document version, heading path, page range, text object key, token count, and content hash.Complete surrounding evidence, stored in object storage with searchable metadata.
Child chunkChild ID, parent ID, vectors, searchable text, original text, page numbers, bounding boxes, and token count.Precise retrieval, reranking, and citation geometry.

Expansion policy

  1. Retrieve childrenRun the current hybrid search and MiniLM reranker over precise child chunks.
  2. Group parentsCombine selected children by parent ID while keeping every child score and citation.
  3. Expand selectivelyFetch a parent only when it adds uncited context within the turn's token budget. Do not expand every hit.
  4. Pack deterministicallyCharge the full parent token count, deduplicate overlapping parents, and keep the repeated-document diversity penalty.
  5. Cite the childAn answer marker still points to exact child geometry. A broad parent page range cannot replace a precise citation.

Compare flat retrieval with child-to-parent expansion on the 24-item suite and the generation support tests.

Ship only if answer support improves without unacceptable citation precision, latency, or token cost.

08 Four deployment sketches

The service boundaries stay fixed. Each cloud maps those boundaries to its strongest managed products.

AWS

Traffic: CloudFront and AWS WAF serve the static UI and route API traffic through an Application Load Balancer.

Compute: ECS on Fargate runs FastAPI replicas. ECS tasks or AWS Batch run Docling ingestion jobs from SQS.

Data: Amazon RDS for PostgreSQL stores conversations and control data. S3 stores private PDFs and parent sections.

Search: Test Amazon OpenSearch Service or OpenSearch Serverless against the exact hybrid contract. Qdrant or LanceDB remain portable alternatives.

Operations: Secrets Manager, KMS, CloudWatch, and a separate Phoenix service with PostgreSQL complete the stack.

OpenSearch Serverless overview

Google Cloud

Traffic: Cloud CDN and the external Application Load Balancer serve the UI and protect the API.

Compute: Cloud Run runs FastAPI with tested streaming timeouts and concurrency. Cloud Run Jobs handles ingestion from Pub/Sub.

Data: Cloud SQL for PostgreSQL stores conversations and control data. Cloud Storage stores private source and parent objects.

Search: Vertex AI Vector Search 2.0 now offers managed hybrid search. Its adapter must still pass the application evaluation suite.

Operations: Secret Manager, Cloud KMS, Cloud Monitoring, and Phoenix on Cloud Run or GKE complete the stack.

Vertex AI Vector Search 2.0 release · Google Cloud RAG reference architecture

Azure

Traffic: Azure Front Door and Web Application Firewall serve the UI and route API traffic.

Compute: Azure Container Apps runs FastAPI. Container Apps Jobs consumes ingestion work from Service Bus.

Data: Azure Database for PostgreSQL stores conversations and control data. Blob Storage holds private source and parent objects.

Search: Azure AI Search runs full-text and vector queries in parallel and merges them with reciprocal rank fusion.

Operations: Key Vault, Azure Monitor, and Phoenix on Container Apps or AKS complete the stack.

Set gateway timeouts and connection draining for server-sent events before load testing.

Azure AI Search hybrid overview · Azure Container Apps overview

Cloudflare

Traffic: Cloudflare CDN, WAF, Access, and Workers provide the edge and customer identity layer.

Compute: Cloudflare Containers can run the existing image, subject to streaming, startup, filesystem, and regional load tests.

Data: R2 stores private PDFs and parent sections. Hyperdrive connects Workers to a managed PostgreSQL provider.

Jobs: Queues dispatch ingestion to Containers. Do not run Docling in a latency-sensitive Worker request.

Search: Vectorize provides managed vector search and metadata filters, but it does not replace the current BM25 path by itself.

Use an external managed hybrid store, or add a measured lexical service and application-level fusion.

Operations: Export application traces to Phoenix in a container platform and keep Cloudflare analytics for edge signals.

Cloudflare Containers · Cloudflare Vectorize

Default shortlist

Start with the customer's existing cloud and identity provider.

If there is no constraint, compare AWS, Google Cloud, and Azure through one load test and one operational cost model.

Use Cloudflare as the edge by default. Use it for the full stack only after its hybrid search and container limits pass.

09 Delivery and proof

Migrate one boundary at a time. Every step has a rollback path and a test that proves the production claim.

  1. Externalize stateMove conversations to managed PostgreSQL and papers to object storage. Run two API replicas without sticky sessions.
  2. Add identityEnforce tenant ownership across chat, documents, search, PDF access, ingestion, traces, and deletion.
  3. Build ingestionAdd the queue, isolated worker, versioned indexes, status API, dead-letter recovery, and atomic promotion.
  4. Shadow managed searchDual-read without affecting answers. Compare results, pages, latency, and cost before switching traffic.
  5. Operationalize PhoenixAdd trace policy, PostgreSQL, authentication, retention, dashboards, alerts, backups, and restore tests.
  6. Canary and scaleRun expected and peak concurrency, provider-failure tests, a canary release, and a complete rollback exercise.
CorrectnessThe 24 retrieval items, answer support tests, conflict coverage, and citation-to-page checks pass.
ScalePeak concurrent streams meet first-token and completion targets without provider or database saturation.
ReliabilityReplica loss, queue retry, OpenAI timeout, search failure, and Phoenix outage each have tested behavior.
SecurityCross-tenant tests fail closed. Secrets, signed URLs, audit records, retention, and deletion are verified.
RecoveryPostgreSQL, object metadata, search indexes, and Phoenix restore within agreed recovery targets.
CostCost per successful answer and per ingested million tokens stays inside tenant budgets at p95 load.

This page is a production plan, not deployed behavior. Product choices remain provisional until these tests produce evidence.
