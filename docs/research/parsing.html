01 What parsing has to deliver

A reader converts a PDF into a Document. On a two-column research paper this is where most of the information is preserved or destroyed, silently, with no error either way.

The corpus is hostile to this stage by design: 27 papers, 425 pages, 137 KB to 12 MB. Two-column Nature, PNAS and Cell layouts where reading order is a guess. Outcome and regression tables, one holding an answer found nowhere else. A seven-paper batch (021-027) adds numbered, LaTeX-set equations as displayed math, not only among figure captions.

Chunking cannot use boundaries the parser never emitted. A citation cannot name a page it did not carry. Retrieval cannot find a table row that arrived as loose digits.

02 The three gates

At 27 documents parsed once, speed and install weight decide nothing. Three properties are pass/fail.

Does it emit heading hierarchy?

Without it, structural chunking is off the table.

Does it carry page numbers?

Without them a citation cannot point at a page, and checkable citations are the product.

Do tables survive as structure?

Without them "which biomarker predicted mortality best" is unanswerable. That answer lives in one table in paper 009.

Three of the six are copyleft — MinerU and PyMuPDF4LLM are AGPL-3.0, Marker is GPL-3.0 — which strikes two of the three strongest scientific-PDF parsers here. Docling (MIT) and unstructured (Apache-2.0) are the only permissive open options. That is most of why the field narrowed.

04 Why five were ruled out

Each on a specific property; the case for each is the one-line case in the table above. Four were never run — rejected on licence, deployment shape or a documented failure mode, and recorded so they can be reopened if a constraint changes. One of them, MinerU, has since been reopened, implemented and run — sections 12 and 13.

MinerU — ruled out on licence and weight, then relicensed, built and run

Against, at the time Heaviest install: model weights, optional GPU path, fatter container. AGPL-3.0. First to re-test if the licence constraint drops.

Since The copyleft blocker went away, so MinerU was run against the same four papers on 2026-07-26. It is no longer an untested candidate, but it is not the recommendation. Results in section 12.

Marker — fast and good, but weakest where the corpus hides its answers

Against Weaker than Docling on nested tables, where several answers live. GPL-3.0.

PyMuPDF4LLM — instant, and fails in the worst possible way

Against No layout intelligence. It fails silently, emitting plausible text with the columns interleaved, which poisons the index. AGPL-3.0.

unstructured — permissive, but the accuracy is in the hosted tier

Against The high-accuracy path is the hosted API; the open version is weaker on two-column, table-heavy layouts.

LlamaParse — best output, wrong dependency

Against API key, per-page cost, and documents leave the machine — wrong for a private research collection. Rejected on deployment shape, not quality.

06 What Docling got right

  • Table reconstruction. The load-bearing capability, and the reason to accept the install weight. TableFormer rebuilt paper 009's answer table as correct 8-column markdown.
  • Furniture removal. 52 page_header and 45 page_footer items correctly classified and stripped on paper 014, so none reaches a chunk.
  • Page provenance in the JSON. 1604 of 1604 items on paper 014 carry a page_no. gate 2 passed.
Known defects

Reading the output surfaced a set of Docling defects. Each needs an automated regression test and a generalized fix before the parser output is trusted. None is fatal; two need checking before ingestion.

Operational note

Docling exits 0 with no output and no error under a restrictive sandbox. The ingestion step needs an explicit assertion that it produced something.

07 The heading-hierarchy problem since fixed — see 11

Superseded — read section 11 alongside this

This section is kept because it is why one config flag is load-bearing, not because it describes current behaviour. Everything below was measured with Docling's default options and still holds under them. With HeadingHierarchyOptions(enabled=True), tested on 2026-07-26, paper 009 comes back as a genuine five-level structure and gate 1 passes. Turn the flag off and all of this returns.

On default options Docling flattened every heading to level 1, and structural chunking depends on heading levels existing. This was the most consequential finding here.

102 of 102 headings came back as level: 1 across the four papers — 18, 31, 1 and 52. It is in the DoclingDocument JSON, not only the markdown export, so no rendering flag fixes it. Paper 009's headings, in order:

Heading as emittedWhat it should be
Methodslevel 2
Study populationlevel 3
Biomarkers · Mortality · Confounders · Imputation · Statistical analysislevel 3
Resultslevel 2
Study populationsame text, different sectionlevel 3
Discussionlevel 2

"Study population" appears twice, under Methods and under Results. Flattened, the two are indistinguishable: a chunk-identity collision and a retrieval problem.

The downstream effect, measured

MarkdownNodeParser derives header_path from heading levels. With every heading at level 1 it is "/" for 100% of chunks — 19 of 19 on 003, 31 of 31 on 009, 48 of 48 on 014. HierarchicalNodeParser falls back to size-based splitting.

This is upstream, not a misconfiguration

Four confirmations: flat levels in the JSON, not only the export; a flat body tree (max nesting depth 1 across 161 direct children); no font or style fields to infer a level from; and a documented open limitation in Docling — discussions #386 and #1170, issue #287. The third-party docling-hierarchical-pdf exists solely to infer this hierarchy.

It was upstream, and upstream is where it got fixed. The same signal proposed in section 08 — glyph height — is what Docling's own option now uses internally.

08 Hierarchy is recoverable from geometry

Docling exposes no typography, but it exposes a bounding box per item. Glyph height separates the levels cleanly on paper 009:

The one defect: multi-line headings inflate, because the box spans both lines — correctable by normalising against line count. Every other level-2 and level-3 heading lands in the right bucket.

What followed

The conclusion at the time: hierarchy is unobtainable from Docling by configuration, but reconstructable from bounding-box geometry in roughly twenty lines. That reconstruction was never written, because Docling shipped the same idea upstream — its HeadingHierarchyOptions font-size fallback is this signal, in the library rather than in our code (section 11). The analysis stands as the reason to trust the option, and as the fallback if it is ever removed.

10 What is still untested

Recorded so the write-up claims no more than was measured.

  • Twenty-three of twenty-seven papers. Four parsed, by both parsers. Reading order verified against the text's own argument sequence on exactly one.
  • Paragraph-level reading order on the multi-page papers. On 003, 009 and 014 both parsers put the top-level sections in the right order, which was checked. Whether paragraphs inside a section stay ordered was not. Docling's scrambling on 011 is therefore a confirmed defect on one layout, not a bound on how often it happens.
  • Equation support remains untested; node provenance is now verified. A real parse of paper 009 through DoclingReader and DoclingNodeParser retained page numbers and bounding boxes in every searchable node. The application bridge adds the source document ID and rejects any node that lacks complete source geometry. Formula support remains open for papers 021-027.
  • Whether equations survive — still fully open, and the four benchmark papers cannot answer it. Both parsers emitted zero formula items across 011, 003, 009 and 014, with MinerU's formula_enable=True. That is the expected result rather than a finding: the manifest records documents 001-020 as "prose- and table-heavy but rarely display typeset mathematics". Papers 021-027 are the real test, added for exactly this: each is confirmed (by extraction, not by inspection) to carry genuine displayed math, and a naive pdftotext pass already corrupts it — a dropped minus sign in paper 023's Langevin equation, an orphaned = in paper 025's regression objective, stranded equation numbers in 022 and 026. Neither parser has been run against any of the seven. Until they are, MinerU's formula recognition is neither confirmed nor refuted, and nothing in this document rests on it.
  • The geometry-based reconstruction. Never written. Docling's own option replaced the need for it, so this is closed rather than pending — see section 08.
  • Whether the two Docling defects MinerU exposes are worth fixing. Caption binding and reading order are repairable in our own code from data Docling already exposes (section 16), but no fix exists and none has been measured.

11 Docling's own fix, tested gate 1 passed

Version 2.106.0 patched the exact defect in section 07. It was run against the same four papers on 2.115.0, and it works: paper 009 comes back with five levels instead of one.

The measurement

With HeadingHierarchyOptions(enabled=True), paper 009's 31 headings distribute as {1:1, 2:6, 3:10, 4:5, 5:9} — exactly the shape section 07 said was missing. The other three papers: 003 {1:1, 2:16, 3:1}, 014 {1:4, 2:5, 3:39}, 011 {1:1} (a one-page letter with one heading).

Docling 2.106.0 (2026-06-23; current release is 2.115.0) added HeadingHierarchyOptions, resolving issue #3633. It rewrites the level field on SectionHeaderItem directly in the DoclingDocument JSON — not only the markdown export — from three signals, in order of precedence:

  1. PDF bookmarks / table of contents, when the file carries one, override everything else.
  2. Numbering markers — a small grammar resolving sequences like "PART I → 1. → 1.1 → (a) → (i)".
  3. Font-size proxy from parsed cell heights, the fallback when no numbering exists — the same signal behind the geometry reconstruction in section 08, now upstream.
Not automatic

Disabled by default — needs HeadingHierarchyOptions(enabled=True). No new dependency, no change to install weight.

Where it can still miss

Style fallback struggles with multi-line or rotated headings. Scanned or VLM-parsed pages carry no font data and degrade to numbering-only — a risk for unnumbered top-level sections like "Abstract" or "Results," common in Nature/Cell house style. Publisher PDFs carrying a bookmark ToC or numbered subsections should be unaffected.

What it fixed, and what it did not

These have to be read together. Reporting only the first would overclaim.

  • The collision that motivated gate 1 is gone. "Study population" appears twice in paper 009, once under Methods and once under Results. Docling now places the two at different levels, 3 and 4, so the two chunks are distinguishable. This is the decisive result: the exact failure section 07 described no longer happens.
  • The levels are usable but not semantically correct. The tree is depth-shifted, not faithful. Discussion and Conclusions land at level 3 beside the Methods subsections when they belong at level 2 with Methods and Results; the Results subsections sit at level 4 rather than 3; back matter runs to level 5. Hierarchy-aware chunking works on this. A reader expecting the paper's own outline does not get it.
  • Journal furniture leaks into the heading list. Docling emits "RESEARCH" and "Open Access" as level-2 headings, above the paper title. They will land in header_path and travel into every chunk beneath them. MinerU's heading list excludes both.

This was the cheapest available test — a config flag against the pipeline already built — and it clears gate 1. It does not settle the parser question on its own, because the same run surfaced two defects that only showed up next to a second parser. Section 12.

Gate 1 — Docling wins, and it is the collision that decides it

MinerU has native heading levels, but a shallow ceiling. On paper 009 its 30 headings are {1:1, 2:29}: the title, then everything else at level 2 — Abstract, Introduction, Methods, Study population, Biomarkers, Statistical analysis, Results, Discussion, Conclusions and all back matter at the same depth.

That reproduces the exact failure section 07 described for flat Docling, one level up. "Study population" appears twice in paper 009, under Methods and under Results. Docling separates them at levels 3 and 4. MinerU puts both at level 2, where they are indistinguishable.

Read the Docling column carefully: it is collision-free but depth-shifted, not a faithful section tree. Discussion and Conclusions share level 3 with the Methods subsections when they belong at level 2. That is enough for hierarchy-aware chunking and not enough to reconstruct the paper's outline. MinerU's one clear advantage here is that it leaves the journal furniture out.

Reading order — MinerU wins on paper 011

Paper 011 is the documented Docling failure from section 06. The letter's argument sequence is unambiguous because the ordinals are written into the text: Insect diapause → In a recent Brief Report → First → Second → Third → Last → While this report. Measured by character offset in each parser's markdown:

  • MinerU 193 < 409 < 754 < 1583 < 2559 < 3218 < 3568 — correct order.
  • Docling emits First → Third → Last → Second. "Second" lands at 2818, after "Third" at 1795 and "Last" at 2463. Confirmed scrambled.
Two limits on this finding

The oracle. pdftotext -layout interleaves the two columns line by line, so its offsets are not a reading-order oracle. The argument sequence is, because the ordinals are explicit.

The scope. On the three multi-page papers both parsers emit Abstract → Introduction → Methods → Results → Discussion in the right order. Docling's scrambling is specific to the dense single-page two-column letter, not systemic. It was not checked at paragraph level on the multi-page papers, so this is a floor on the defect, not a proof of its rarity.

Tables — split, and one correction to make

  • The answer table survives in both. On 009 MinerU emits it as HTML (<table><tr><td>), Docling as markdown. The answer — epigenetic clock, HR 1.40, highest of the biomarkers — is intact either way.
  • Caption binding: MinerU wins. The defect recorded in section 06 is still live in Docling 2.115.0. On paper 009 Table 2 and Table 3 have zero captions bound, and Table 1's caption text is duplicated into the table body. MinerU binds captions correctly, as a separate table_caption field, on both tables it found.
  • Recall: split. Docling finds 3 tables on 009 to MinerU's 2 — it also picks up the abbreviations table. On 014 MinerU finds 10 where Docling finds 0.
Correction — paper 014 does have tables

This document has recorded 014 as containing zero tables. That is true of the article body only. All ten tables MinerU finds are on pages 28–31, in the Nature Reporting Summary appended to the paper, which is genuinely tabular — they are real, not hallucinated. They are also boilerplate, so recall here is not obviously a gain for retrieval.

What this run could not test

Formulas — these four papers cannot answer the question

Both parsers emitted zero formula items on all four papers, with formula_enable=True on MinerU. That is the expected result, not a finding: none of these four papers contains displayed mathematics. The corpus manifest records documents 001-020 as "prose- and table-heavy but rarely display typeset mathematics", which is precisely why papers 021-027 were added. Formula recognition is the one capability this document has repeatedly credited to MinerU alone, and it stays untested — measuring it here would prove nothing in either direction. Papers 021-027 are the test; section 10 holds the open question, and nothing in section 16 rests on it.

13 What MinerU costs measured

The capability comparison is close enough that cost decides it. Cost is not close.

40×slower on paper 014
453.4 s014, MinerU on MPS
11.4 s014, Docling
~2.6 GBpipeline model weights

Extrapolated over the corpus: Docling 5–8 minutes, MinerU roughly 1.5–2.5 hours. Both extrapolations were made against the 327-page figure, so both are floors — the corpus is now 425 pages. MinerU was running on MPS, its accelerated path, not CPU.

Install and dependency pressure

  • The right extra is mineru[pipeline]==3.4.4. mineru[core] was installed first and is wrong for us — it pulls gradio and the VLM torch path. The venv reaches 1.4 GB total; pipeline weights are ~2.6 GB downloaded from HuggingFace on first run (measured against the HF API; MinerU's own docs ask for 20 GB+ free disk).
  • It pulls the stack backwards. Installing MinerU downgraded starlette 1.3.1 → 0.52.1, transformers 5.8.1 → 4.57.6, pypdfium2 5.12.1 → 5.10.1. Nothing broke — the full suite still passes — but it pins transformers>=4.57.3,<5, which will fight a future embedding model. torchvision is unpinned against torch>=2.6,<3, the classic MinerU install failure.

Operational hazards found while building it

  • It renders pages in a ProcessPoolExecutor. On macOS, which spawns rather than forks, any entry point must be import-safe or the run dies with BrokenProcessPool. Hit directly on the first smoke run. Uvicorn is fine; ad-hoc scripts are not.
  • Silent empty output on macOS. Open issues #5311 and #5324: every model stage reports 100%, then no pages and no exception, on larger PDFs. Workarounds are chunking to ~40 pages or MINERU_PROCESSING_WINDOW_SIZE=16. Not observed on our 32-page paper. This is the same failure shape already recorded for Docling under a sandbox. It needs a regression test that treats empty parser output as a failure.
  • OCR language has no auto. en normalises to MinerU's ch model, which is the Latin+CJK recogniser — correct for English papers despite reading wrong.
  • The default backend is hybrid-engine, not pipeline. Hybrid and VLM cannot run pure-CPU, so pipeline is selected explicitly.

Licence — the blocker is gone, the stability is not

MinerU moved off AGPL-3.0 to the "MinerU Open Source License" (Apache-2.0 based) at 3.1.0. The copyleft objection that ruled it out in section 04 no longer applies to our pinned version. Three qualifications belong beside that:

DateLICENSE.md change

  • The relicensing wobbled. Four changes in under four weeks, including a reversion. Forward licence stability is an open risk, not a settled question.
  • Some weights are still AGPL. opendatalab/MinerU2.5-2509-1.2B is tagged agpl-3.0 on HuggingFace today; only MinerU2.5-Pro-2604/2605 are Apache-2.0. Anything at or below 3.0.x is AGPL code and AGPL weights. Our pipeline backend does not use those VLM weights, but any version bump needs the model tags re-checked.
  • An active obligation Docling does not carry. Offering an online service built on MinerU requires prominently disclosing that MinerU is used. The other thresholds (100M monthly active users, $20M monthly revenue) are irrelevant at this scale; the disclosure is not.

15 Why the others don't replace Docling

Each ruled out on a specific, confirmed property, not a hunch.

GROBID — the best hierarchy of any candidate, but it can't do tables

For Purpose-built for scholarly structure: real nested <div> sections from cascaded sequence-labeling models, not a layout heuristic. Apache-2.0, actively maintained.

Against One benchmark measured its table extraction at a GriTS score of 0.12. It cannot process figures at all. The corpus's load-bearing answer lives in a table (paper 009) — this alone disqualifies it as a primary parser.

Nougat — dormant, non-commercial weights, no structure

Against Code is MIT, but the released weights are CC-BY-NC — not open end-to-end. Last commit 2025-02-21, effectively dormant. Output is a single markdown text stream with no section hierarchy and no page provenance — solves equations, nothing else this job needs.

PaddleOCR / PP-Structure — plausible on tables, unproven on hierarchy, friction on install

For Apache-2.0. Lightest model footprint of the group by a wide margin; table recognition a stated strength across versions.

Against Nested heading-level output not confirmed from documentation. Runs on PaddlePaddle, not Torch — a thinner English-language ecosystem, and the official PP-StructureV3 example was found broken in at least one open issue. Not ruled out on a hard defect — unproven, would need hands-on testing before trusting.

olmOCR 2 — the cleanest licence of any candidate, wrong operational shape

For Apache-2.0 for code and weights, no thresholds or asterisks — the only fully unrestricted licence found. Tables as HTML, equations as LaTeX, forced JSON page metadata.

Against A 7B vision-language model needs a real GPU (20 GB+ VRAM recommended) and vLLM to serve. Disproportionate for a one-time 20-paper batch that Docling clears CPU-only in 5–8 minutes. No confirmed page-anchored provenance per element.

Surya — Marker's own engine, already found wanting

Against Code Apache-2.0, but released weights carry a modified RAIL-M licence (free under $5M funding/revenue, not unrestricted). Same lineage as Marker, already measured weaker than Docling on nested tables — no reason to expect standalone Surya to do better without testing, and the weights licence adds a reason not to bother first.
