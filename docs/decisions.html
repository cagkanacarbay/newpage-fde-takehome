01 PDF parsing: Docling

Use Docling to parse the research corpus. Keep MinerU only as a reproducible comparison baseline.

TL;DR

What: Parse each born-digital source PDF with Docling, do_ocr=False, and HeadingHierarchyOptions(enabled=True).

Why: Docling preserves page metadata and the key table, provides usable heading depth, runs locally, is MIT licensed, and was 40 times faster than MinerU on paper 014. Research evidence.

Status: Provisional. The application bridge adds each source ID and verifies node page numbers and bounding boxes. Formula support remains open. Open research.

How we use Docling

Enable heading hierarchy on every parse

Pass HeadingHierarchyOptions(enabled=True).

Default Docling output makes every heading level 1. The option restores usable nested headings without another dependency. Research evidence.

Keep page provenance through the node layer

Keep page_no from parser output through LlamaIndex nodes before we offer page-level citations.

Docling emitted page data for every measured item. The application bridge now verifies that DoclingReader and DoclingNodeParser retain the page number and bounding box in node.metadata. Integration path.

Fail ingestion when parsing returns no content

Reject an empty parser result even if the process exits successfully.

Docling can exit without output under a restrictive sandbox. Research evidence.

Do not hide known Docling defects

Paper 011 has a reading-order error. Paper 009 has two unbound table captions and one duplicated caption.

Do not add a repair until a regression test proves it. MinerU output is the comparison reference for both cases. Research evidence.

Use MinerU only as the comparison baseline

Do not add MinerU to the application ingestion path.

MinerU preserves paper 011 reading order and table captions. It emits no heading level deeper than 2 and took 453.4 seconds where Docling took 11.4 seconds. Research evidence.

Revisit the choice only after the remaining tests

Run both parsers on papers 021 through 027 before deciding formula support.

Reconsider Docling if MinerU preserves equations where Docling does not, if MinerU adds deeper headings, or if Docling regresses on hierarchy. Test Kreuzberg only if a material gap remains. Research evidence.

02 Observability: Arize Phoenix

Use Arize Phoenix as the local observability surface for the demo.

TL;DR

What: Run Phoenix locally in one container and expose its trace interface through its normal port.

Why: It makes the RAG pipeline visible without adding a large service stack or requiring an external account.

Status: Decided for the demo.

What the demo shows

Retrieved chunks and source metadata

Trace retrieval inputs, selected chunks, scores, document IDs, and citation metadata.

LLM prompts and responses

Trace the complete generation call so prompt behavior and citation failures can be inspected.

Pipeline latency

Show parsing, retrieval, and generation spans so slow stages are visible.

Production revisit trigger

Revisit the deployment when retention, access control, team workflows, or managed operations become requirements.

Keep instrumentation portable through OpenTelemetry and OpenInference conventions.

03 Embedding model: OpenAI text-embedding-3-large

Use text-embedding-3-large for document and query vectors in the 27-paper corpus.

TL;DR

What: Request 3,072-dimensional vectors from OpenAI text-embedding-3-large during ingestion and retrieval.

Why: The first local Qwen full-corpus run took 58 minutes and produced no index. Its termination was consistent with memory pressure. The OpenAI path removes local embedding weights and uses the API key already required for generation.

Limits: Each final contextualized input must stay within 8,192 tokens. The adapter batches requests by input count and total tokens. OpenAI embeddings API reference.

Status: Decided for the demo. The verified build indexed 696 chunks from all 27 papers in about six minutes. It produced a 30 MB LanceDB index with 3,072-dimensional vectors.

How we use the model

Keep index and query vectors compatible

Set model="text-embedding-3-large" and dimensions=3072 for every request.

Use the same adapter for ingestion and query retrieval. Never query an index built with another vector shape.

Keep contextual chunks inside the model limit

Tokenize with cl100k_base and let Docling split structural units above 7,500 tokens.

Reject any final contextualized input above the 8,192-token model limit before making an API request.

Keep local tests independent from OpenAI

Use an OpenAI-compatible local endpoint for process tests and injected clients for adapter tests.

Use the real API only for the explicit full-corpus build and live retrieval verification.

Reopen the choice from measured failures

Measure gold-paper recall, MRR, distractor rank, index time, input tokens, and query latency.

Reconsider the model if retrieval quality fails, policy blocks external processing, or corpus cost exceeds the deployment budget.

04 Vector database: LanceDB

Use LanceDB as the embedded vector store for the local Docker demo.

TL;DR

What: Store the demo index in LanceDB and use its dense, full-text, and hybrid query modes.

Why: It adds no service to Docker, supports the measured hybrid retrieval direction, and has a mature LlamaIndex integration. Research evidence.

Production: Revisit LanceDB Cloud and Qdrant Cloud when the deployment target becomes concrete. The current LanceDB integration does not support hybrid queries against LanceDB Cloud tables.

GitHub: Issue 14 is closed.

Status: Decided for the demo.

How we use LanceDB

Keep the demo embedded

Run LanceDB in process and persist the local index with the application data.

The 27-paper corpus is about 1,100 chunks, so a separate database service adds no value for this demo.

Use hybrid retrieval

Use LanceDB dense and BM25 capabilities for the measured hybrid retrieval path.

Keep the retrieval adapter separate from storage so diversity policy and later store changes remain easy to test.

Revisit the managed path in production

Compare LanceDB Cloud and Qdrant Cloud when deployment, scale, and service boundaries become requirements.

Do not treat the current LanceDB Cloud integration as a hybrid production path until its limitation is resolved or measured around.

05 Retrieval: broad hybrid candidates, then evidence packing

Retrieve broadly, rerank the candidates, and pack the strongest evidence by token budget.

TL;DR

What: Plan zero, one, or several semantic and lexical queries. Retrieve broadly, rerank, and pack complete evidence units by tokens.

Why: Exact entity search and semantic similarity need different query forms. Simple and multi-paper questions need different amounts of evidence.

Configuration: Keep candidate depth, document diversity, reranking, and source budget as evaluation values.

Evidence: 2026 conversational-retrieval research supports query planning and multi-aspect queries. Corpus-specific quality remains untested.

Status: Direction agreed. Retrieval research and open values.

How we retrieve

Plan lexical and semantic queries separately

Use complete semantic queries for embeddings and exact scientific anchors for BM25.

Allow several queries for a genuine comparison or multi-part request.

Use deterministic chunk context

Prepend paper, section, element, caption, and page labels before dense and BM25 indexing.

Keep original chunk text separate for answers and citations.

Choose context by evidence tokens

Do not use a fixed final chunk count or hard per-paper cap as a product rule.

Tune candidate depth, document diversity, and source budget against the full evaluation set.

Do not claim unarchived quality

The evaluation page defines six contradiction pairs and 24 total items.

No repository artifact proves that any retrieval variant passed all six pairs.

Evaluate model-based reranking only when needed

Start with hybrid rank fusion and a deterministic query plan.

Add a cross-encoder only when corpus evaluation shows a ranking failure.

06 Guardrails: corpus-only, verified answers

The assistant can state only what the research corpus supports, and every factual claim must pass source verification.

TL;DR

What: Gate retrieved chunks before generation, require a citation for every factual claim, and verify each claim against its cited text.

Why: Live Long R&D needs a research assistant, not a general chatbot. A fluent answer without paper support is a product failure.

Boundary: User prompts control the answer form. They cannot override retrieval, evidence, citation, conflict, medical, or prompt-injection guardrails.

Status: Policy decided. The calibrated score and smaller verifier model remain implementation choices.

GitHub: Issue 21 - define assistant guardrails records the agreed policy. The technical-choice analysis preserves the alternatives and implementation limits.

What the system enforces

Separate guardrails from prompt guidance

Guardrails are deterministic or systematic controls around the model. A user cannot turn them off through a chat message.

Prompt guidance controls presentation. The user can request a synthesis, a summary, a simple answer, or a detailed answer.

The default is a detailed, source-specific answer. The prompt can change its form, but it cannot change its evidence boundary.

Filter retrieval before the main model sees evidence

Calibrate a relevance threshold with both answerable and irrelevant test questions. The earlier 0.75 value is an example, not a fixed score.

Raw hybrid RRF scores are not relevance probabilities. The final threshold must use a stable score with measured meaning.

Remove every chunk below the calibrated threshold. The main model receives only passing chunks, even when the top result passes.

If no chunks pass, do not call the main model. Return that retrieval found no sufficiently relevant evidence in the corpus for the question.

Retrieval evaluation must test known contradiction pairs and confirm that evidence for both sides reaches generation.

Keep every answer inside the papers

The papers are the complete factual domain. The assistant cannot fill a gap with model knowledge, common knowledge, or an uncited explanation.

Use clear evidence fully. Preserve exact values, units, cohorts, conditions, outcomes, limits, and other details when they answer the question.

Do not replace clear information with a vague abstraction. Synthesize only when the user asks or when synthesis helps answer the question.

Disclose every material conflict in the retrieved evidence. State what each source reports and preserve its conditions and uncertainty.

Reject personal diagnosis, treatment, or dosing advice. When useful, report the exact study evidence and study context without personalizing it.

Treat retrieved text as data, never instructions

Put system instructions inside an <instructions> block. Put retrieved paper text inside a separate <data> block.

Tell the model that content inside <data> is evidence only. It must never follow instructions found there.

Escape structural delimiter text before prompt assembly. The fixed corpus is curated, but corpus trust does not turn evidence into instructions.

Verify every factual claim through structured evidence
  1. Generate structured claimsThe main model returns atomic factual claims with citation IDs from the retrieved set.
  2. Read the answer and cited chunksA smaller verifier reads the complete answer, then checks each claim only against its cited chunks.
  3. Return exact evidenceFor each claim, the verifier returns a structured status, chunk ID, and exact supporting text from that chunk.
  4. Validate deterministicallyCode rejects unknown IDs, missing provenance, and evidence text that is not an exact substring of the cited chunk.
  5. Clean without changing meaningThe reviewer removes rejected claims and adjusts connective text only. It cannot add facts, change values, or change citations.

The substring check proves that the evidence text exists. The smaller verifier still decides whether that text supports the claim.

Keep uncertainty stated by a source. Remove a claim when the verifier cannot confirm that its cited text supports it.

Do not run another model review after cleanup. Run the response schema and deterministic citation checks before returning the answer.

Fail closed without hiding what happened

If some requested parts lack support, return the supported answer and identify the specific gaps in the retrieved evidence.

If cleanup removes every factual claim, return that the retrieved evidence did not provide a supported answer.

If the verifier times out or returns invalid output, return a verification error. Never return the unverified draft.

07 Context management: 100k-token history window, SQLite storage

Keep the recent conversation verbatim within a generous token budget, tell the user when anything drops, and let the query planner decide what each turn needs.

TL;DR

What: Keep the most recent turns verbatim within a 100k-token history budget. Drop oldest turns beyond the budget, with an inline notice to the user. Persist conversations in SQLite, bind-mounted outside the Docker container.

Why: The model context window is large, so capacity is not the constraint. Demo-length conversations do not need summarization or retrieval over history, and a plain token window keeps every referenced entity verbatim.

Status: Strategy decided. Issue 22 - context management strategy records the grilling.

How context is managed

Window by tokens, not by turn count

Keep the newest turns verbatim until adding the next older turn would exceed 100k tokens.

There is no fixed turn limit. Short turns give a long memory; long turns give a short one.

Summarization and retrieval over history are rejected for v1. Both can mangle the exact entities, doses, and paper IDs that follow-up questions reference.

Never truncate silently

When turns are dropped to fit the budget, place an inline notice in the conversation.

No permanent token meter and no near-cap banner. With a 100k budget, hitting it is rare.

Let the query planner decide what a turn needs

The QueryPlan step from the retrieval contract reads the message and the history and decides the evidence need per turn.

A meta-question about the conversation itself, such as "what did it say earlier?", retrieves nothing and is answered from history alone.

The default posture is to give the model everything within budget. Evidence packing must account for the actual history size of the turn.

Resolve follow-ups for retrieval, not for the answer

The planner resolves references such as "the second paper" or "it" into explicit retrieval queries.

The answer generator sees the windowed history and the retrieved evidence only. The resolved standalone question stays internal to retrieval, so the answer addresses the message as asked.

Persist conversations in SQLite outside the container

Store every conversation in a SQLite database.

Bind-mount the database file from the host, so it survives the container. This is a one-line volume for the reviewer.

08 Quality controls: three deterministic retrieval gates

The v1 quality gates are a hand-authored, deterministic retrieval suite over the 27-paper corpus. No LLM judge, no API keys.

TL;DR

What: Three gates scored at document-ID level in the top 10. Gate A, contradiction coverage: both sides of 6 disagreeing paper pairs must be retrieved. Gate B, entity recall: for 6 planted lookalike traps, the gold paper must rank above each named distractor. Gate C, gold-document hit rate: 12 single-source questions must surface their gold paper.

Why: The corpus was built with papers that disagree and entities that look alike. These gates test those planted failure cases deterministically, so a retrieval regression fails CI without any model in the loop.

Thresholds: 6/6, 6/6, and 11/12 with item C1 mandatory. Provisional until the k = 10 calibration run. Research evidence and full item set.

GitHub: Issue 20 - choose the v1 eval suite records the decision.

Status: Decided for v1. Building the suite is post-map execution.

How the gates run

Thresholds are provisional until the calibration run

The first run goes out at k = 10 and its job is inspection: what does the retriever actually return for each query?

Quotes that real retrieval output beats get corrected against that output. Only then are the thresholds and the final k per gate fixed.

Run as a blocking, path-scoped CI job

The suite uses pytest. Deterministic checks use embedding doubles and isolated indexes. Live checks record the OpenAI model, index build, and retrieval depth.

GitHub Actions runs Python, container, and web validation for every pull request and push to main. A path-scoped retrieval gate remains a future refinement.

Citation-level gates are v2

Gate A requires both sides retrieved. The bar becomes both sides cited only when the answer-generation slice lands.

LLM-judge metrics such as faithfulness and answer correctness are a later consideration, not v1.

Gate C stays at 12 items

No growth to one item per paper in v1. Gates A and B already touch 18 of the 27 papers, and the marginal coverage per added item does not justify the authoring cost.

09 Packaging: one indexed application image

Ship the static chat UI, API, and completed LanceDB index in one image.

TL;DR

What: Build the image with data/index as a named Docker context. Serve the exported Next.js UI and FastAPI from port 8000.

Why: A reviewer starts one container and receives the exact 696-chunk index. LanceDB needs no separate database service.

Security: Pass OPENAI_API_KEY only at runtime. The build context excludes .env, the corpus, local caches, and model weights.

Size control: Keep Docling, Torch, and parser integrations in the ingest dependency group. Exclude that group from the runtime image.

Status: The verified 197 MB image contains 696 chunks. It loaded the UI and returned live citations from papers 017, 015, and 016.
